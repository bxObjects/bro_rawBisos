Design (user's model, refined with Claude, agreed 2026-10-19):
- A platform may have many PALS-BXOs, some not activated (not cloned from GitLab yet); each PALS-BXO
  may have many CBMs. Utilities that manage both are in bisos.pals: =palsOfSys.cs=.
- Three places, split by who owns the state:
  | Place                                   | Kind | Holds                                          |
  |-----------------------------------------+------+------------------------------------------------|
  | =/bisos/platform/sys/pals/<palsBxo>/=     | host | =path/value= (absent: not activated),           |
  |                                         |      | =origin/value= (where to clone it from)         |
  | =<palsBxo>/sys/cbm/<cbmName>/=            | repo | =capabilityType/value= (hereWeb ...),           |
  |                                         |      | =cbsSpec/value= (relative to the PALS-BXO root) |
  | =/bisos/platform/sys/cbm/pals/<palsBxo>/= | host | generated CBM leaves =<cbmName>/=: cbmProc.spcs, |
  |                                         |      | cbmProc.control (gate), cbmProc.status         |
- Why the split: the gate (enabled/available/disabled) and the status log are per-host decisions and
  outcomes; in a shared PALS-BXO they would make every materialization a commit. The PALS-BXO only
  declares; the platform holds state, as standard CBM leaves (the =pals= realm of rawBisosCBMs), so the
  existing walker and cbm_* verbs work unchanged.
- Values are FileParams (=<name>/value=). cbsSpec is relative (hosts check out at different paths);
  the platform's path/value is host state, so absolute. Entries are named by capability
  (=libreHalaal=), not by why they exist.
- =palsOfSys.cs=: palsList (each PALS-BXO, activated or not, and its CBMs), palsAdd <bxoPath>
  [--origin=], palsCbmsList [pals], palsCbmAdd <pals> <name> <cbsRelPath> --type=, palsLeavesPlant
  (generate/refresh platform leaves from the lists; idempotent; never overwrites a gate or status),
  later palsActivate <pals> (clone).
- Trigger: sysCbmManage fullyMaterialize walks only collective/hereWeb (sysCbmManage_csu.py:225); it
  must also walk the pals realm, after collective (nginx, Node) and before platform.here (its snapshot).
  Preferred: in bisos.capability, so one command still does everything.
